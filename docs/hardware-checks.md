# Hardware checks

CI builds this project but has no GPU. These checks are the evidence that the
hardware layer works. Run them on the real machine, record the date and
driver version below, and fill in the Result column for each row.

Checks 3-6 write to the GPU (clock offsets) through NVAPI, which
refuses those calls without administrator rights. Run `gao.exe` from an
**elevated** PowerShell or Command Prompt (Start menu -> right-click
PowerShell/Terminal -> "Run as administrator") for any command marked
"yes" in the Elevated column below; an unelevated shell is expected to fail
those specific calls with an NVAPI error, not a crash. Checks 1-2 only read
telemetry through NVML and do not need elevation. Checks 10-12 need no
elevation either: the stress load only computes, it writes no settings.
Checks 13-16 run `--optimize`, which writes clocks and the power limit: elevated.
Checks 46-52 run `--optimize` as well and need an elevated shell; check 45 compares `--probe` with another tool.
Checks 54-56 exercise the window after its display device went away; 54 and 55 change no GPU setting, 56 does run a search (from the window, elevated), which writes clocks and the power limit.
Checks 17-22 cover persistence; 19 and 20 need a log-off and log-on.

Commands assume a Release build at `.\build\Release\gao.exe` from the repo
root; adjust the path for a Debug build.

## Notes

- **Check 6 is the one that matters.** If a write NVAPI accepts cannot be
  distinguished from one it applies, the search cannot be trusted, and the approach needs rethinking before
  more is built on it. `--set-core 5000` (5 GHz above stock) is expected to
  be silently ignored by the driver; `gao` must print `MISMATCH`, never `OK`,
  for that request.
- Run check 4 (`--reset`) again after check 6 to leave the card in a known
  state, since a refused write can leave the read-back at whatever the
  driver's own limit clamped it to rather than exactly the requested value.

### Checks that involve a driver reset

A driver reset that `gao` survives is not by itself a pass. Round A of check 51
showed why: the tool survived the reset and the desktop was unusable afterwards.
A check that involves a driver reset (51, 52; for 54, 55 and 56 see their rows) passes only when all four of these
hold:

1. **`gao`.** The run ends with a `RESULT:` line: the applied values, or
   `RESULT: not applied -- <reason>` with one of the reasons below. `gao.exe`
   does not crash. The card is at the result or at stock, and `gao --status`
   agrees. The journal has no `begin` without a `complete`.
2. **The Windows System log.** At most one driver reset (nvlddmkm) during the
   run, or two when the first came in the memory search and the core was
   searched after it, unless the run ended with `the driver reset twice`,
   `the driver reset three times`,
   `the card was not usable when checked after a driver reset (...)` or
   `the card computed almost nothing after a driver reset`. `gao` may count one
   more reset than the System log shows: it also counts a stalled or blind
   probe, a refused write and a failed bandwidth measurement on an overclocked
   candidate, which only suggest a reset. Bandwidth readings that did not
   settle are not counted: the load measured, and the memory scan ends there.
3. **The desktop.** Within one minute after the run ends, the windows that were
   open are visible and usable, a new program can be started and shows its
   window, and no sign-out or restart was needed. Programs that crashed are
   noted.
4. **The owner's judgement.** The machine feels normal afterwards.

The reasons a run can end with after a driver reset, all with the card at stock
and nothing saved: `the driver reset twice`; `the driver reset three times`;
`the driver reset at stock clocks (...)`;
`the card did not recover after a driver reset`;
`the card was not usable when checked after a driver reset (...)`;
`the card computed almost nothing after a driver reset`;
`the driver did not come back after a reset`;
`could not set the card to stock while recovering`;
`aborted`; `soak failed 4 times`. When the reset to stock
itself failed, the `RESULT:` line says so instead of `(card at stock)`.

None of the reset handling beyond what round A showed has been run on hardware.
In particular it is not known whether the 20 s rest keeps the desktop usable:
there is one observation of an unusable desktop, it came from a forced reset
(`dxcap -forcetdr`), and nothing has been re-run since.

For checks 51 and 52, record whether a tray app was running during the check
and which build it was: an installed v0.2.0 with its window open can itself
crash at the forced reset.

Check 33's re-run pass was recorded on a build whose recovery of the window's
device did not call `ClearState` and `Flush` on the old device context; the
recovery now does (`release_device()` in `main_gui.cpp`), on the path a reset
takes while the tray app runs, so check 33 and the reset half of check 41 (no
result is recorded for it here) must both be run again on this build before
their results are relied on.
